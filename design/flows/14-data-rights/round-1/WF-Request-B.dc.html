Structure B — the correction is a form page of its own

The request page lists the corrections recorded, with Record a correction (a link) opening /admin/data-rights/{Id}/corrections/new (PROPOSED route; trail Home › Data rights requests › [id] › Record a correction). Save returns to the request with the result focused over the list. Complete request stands in an end section of its own, apart from the list (flow 13's end section).

The form page chooses the record from a list of places, each saying where it is changed and linking there when the caller may open it (Q2).

Changes and why

  • PROPOSED: a route, a page, the Coordinator allowed (Q1), the refusal words.
  • DATA: a fixed list of correctable places and their owning page (Account › First name, Last name, Email; Trainee profile › Programme start, Curriculum; Other), and whether the caller may open each.
  • "Other" keeps ApplyRectification's free text, so nothing is lost.
  • Room on the form page for the before value read back where the page knows it (DATA, round 2).

Steps (presses + fields typed), from the queue's row

  • Carry a correction through: 5 + 2 at 1280 (Review; Record a correction; choose the record; before, after typed; Save; Complete request). 5 + 2 at 390.
  • Five corrections: 4 presses + 2 fields each, one page load each way.
